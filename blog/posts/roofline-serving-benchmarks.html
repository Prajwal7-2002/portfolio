Roofline Benchmarking & Auto-Tuning LLM Serving: How We Pushed Pure PyTorch to 27 tok/s

Most engineers treat LLM serving as an opaque black box—guessing thread counts, setting arbitrary batch sizes, and hoping VRAM doesn't crash. Here is how empirical roofline modeling and batched paged KV-cache gather eliminated DRAM memory bandwidth waste.

c=1 throughput: 8.5 tok/s c=4 throughput: 26.4 tok/s (3.1×) energy: 1.77 Tok/Joule (GPU power) gpu power: 14.9 W gpu: RTX 3050 6GB Laptop

Update (2026-11-05). The original results in section 3 were measured on mini-infer v0.2.1, which had two bugs I have since fixed:

  • Prefix-cache hits produced wrong output (fixed in v0.2.8).
  • Cached prompts were never evicted, so a long-running server eventually ran out of KV memory and dropped requests (fixed in v0.2.9).

The original 12-request runs were too short to hit the second bug. I re-measured v0.2.9 with 24 requests per level, ~286-token prompts and 128 output tokens. Results are in section 3:

  • Throughput: 8.5 / 15.3 / 26.4 tok/s at 1 / 2 / 4 users, 24/24 requests OK.
  • Energy: 1.77 tokens per joule at 4 users (GPU power only).

Two corrections:

  • Bandwidth: the 6 GB RTX 3050 laptop GPU has a 96-bit memory bus, so it peaks at 168 GB/s, not 192. My unit runs its memory at 10.8 Gbps, about 130 GB/s (121.5 GB/s measured with a copy benchmark).
  • Energy: I removed an unsupported comparison with cloud instances.

1. The Fundamental Memory-Bandwidth Bottleneck

Autoregressive LLM generation is overwhelmingly memory-bandwidth bound. During single-token decoding, every forward pass reads the model's entire weight matrix from GPU DRAM into on-chip cache just to emit a single token:

$$\text{Arithmetic Intensity} \approx \frac{2 \times P \text{ FLOPs}}{2 \times P \text{ Bytes}} \approx 1 \text{ FLOP / Byte}$$

On an entry-level consumer laptop GPU like the NVIDIA GeForce RTX 3050 6GB Laptop (96-bit GDDR6: at most 168 GB/s; about 130 GB/s on my unit), theoretical peak decode speed for a 0.5B model in bfloat16 (1 GB of weights) is strictly capped by how fast weights stream from DRAM: 

Theoretical Max Decode ≈ 130-168 GB/s / 1.0 GB ≈ 130-168 tokens / second (unbatched upper limit)

However, in naive Python serving runtimes, request concurrency often tanks generation speed rather than accelerating it. Why?

2. The Serial Iteration Flaw vs. Unified Batched Decoding

In naive continuous batching architectures, active sequences are stepped in a serial loop: 

# Naive unbatched loop: Reads weights from DRAM 4 times per step!
for seq in active_sequences:
    token = model.forward(seq.current_token, seq.kv_cache)

When 4 requests run concurrently, the GPU reads the entire 1 GB model weights from DRAM 4 separate times every single iteration step.

In mini-infer v0.2.1, we introduced zero-copy physical block gathering: 

# mini-infer v0.2.1: Unified [B, 1] forward pass
k_all, v_all, mask = block_pool.gather_batched_paged_kv(
    layer_idx=layer, block_tables=tables, context_lens=lens, device=device
)
# Weights are read from DRAM exactly ONCE per iteration across all 4 sequences!
logits = model(tokens_batch, k_all, v_all, mask)

For comparison, Ollama (llama.cpp) serves the 4-bit version of this model at ~190 tok/s on the same GPU.

4. Key Systems Takeaways

  • Unified Batched Gather Pays Off Under Load: 4 concurrent users get 3.1× the throughput of 1 user (8.5 → 26.4 tok/s), while each user's TPOT rises only 29%, because weights are streamed from DRAM once per step instead of once per sequence.
  • Energy Scales With Batching (1.77 Tokens / Joule): GPU power stays near 14-15 W from 1 to 4 users, so tokens per joule rise almost 3× with batching (GPU power only; the rest of the laptop is not counted).
  • The Next Bottleneck Is Python, Not DRAM: at ~32% GPU utilisation, the gap to the 130-168 tok/s bandwidth ceiling is dispatch overhead. Fusing the per-layer paged-KV gathers (or CUDA graphs) is the next step.
  • Automated Auto-Tuning: Using servebench tune, developers can detect saturation knees automatically and prevent latency degradation before deploying to production.
